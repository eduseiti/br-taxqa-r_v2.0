## 1. Execution

### 1.1 Probe (≈ $0.011)

- **`openai/gpt-6.2-sol:batch`** on `chat/completions`: refused with HTTP 404 ("cannot be used with the
  chat/completions endpoint (adapter OpenAIBatchAdapter)"). It is an asynchronous id only, so no cost. OpenRouter's
  Batch API is `POST /api/v1/batches`:
  - the requests are inline, with no file upload;
  - one model and one endpoint per batch;
  - the results come back inline in `GET /api/v1/batches/{id}`;
  - usage is reported per request, cost only per batch;
  - there is no cancel endpoint.
- **The batch-level `provider` accepts only `only` and `allow_fallbacks`.** `require_parameters` and
  `data_collection` are refused there (HTTP 400), so they stay in each request body. OpenRouter may not apply them
  there. The checks that matter are made on the replies themselves:
  - served provider OpenAI on every result;
  - no tool use;
  - billed cost = token cost at $1 / $5, exactly. The batch was billed $0.010859 for 4,574 input and 1,257 output
    tokens.
- **Reasoning:** `effort: none` is refused synchronously and in batch (the batch failed before any cost).
  `minimal` is accepted.
- Knowledge cutoff: not in the catalogue, and not probed (informational only, plan §5.4).

### 1.2 Client changes (no change to any existing request or cache key)

- **`llm_client/client.py`:** `LLM.body()` builds the OpenRouter batch body: the synchronous body without `model`,
  with `provider` keeping only the keys the batch level refuses. Batch queueing is enabled for `openrouter`.
- **`llm_client/batch.py`:** OpenRouter submit, poll and collect.
  - Each result is checked like a synchronous reply: tool use, served provider. A failed check is ledgered as
    `rejected:` and not cached.
  - Ledger rows are `batch:` rows at half the list price.
  - The job record keeps OpenRouter's reported `usage` next to the ledger sum (`usd_rows`), so the two can be
    reconciled.
  - `BatchRecorder(max_requests=…)` splits a queue into several jobs.
  - Keys that are still in an open job are not queued again.
- **`rag.py`:**
  - `run`/`generate --batch [--batch-max N]` queues the uncached calls and submits; nothing is written until the
    rerun.
  - `rag.py batch status|wait` polls and collects into `runs/answers/cache`. Job records are in
    `runs/answers/batches/` (gitignored, like `runs/**`).
- **Tests:** 2 new OpenRouter batch tests (submit split, collect, ledger, provider mismatch). The suites pass:
  llm_client 15, rag 53, nuggets 19.
- **`scripts/rag/llms.yaml`:** entry `gpt-6.2-sol`.
  - Price $2 / $0.10 / $10 list with `batch_discount: 0.5`; model `openai/gpt-6.2-sol`; effort `minimal`;
    `only: [openai]`.
  - Comments record the probe findings.
- **Experiment file:** `scripts/rag/experiments/sol.yaml`.

## 3. Reading

1. **The newer, stronger model knows the P&R content better.**
   - Closed book, Sol beats Terra by +0.09 V_strict, and beats every RAG condition of every earlier generator.
     Terra's best is the oracle at 0.366.
   - It also contradicts the gold answer three times less often without retrieval.

   Memorisation of the public P&R 2024 can't be excluded: it is part of "parametric knowledge" (citation plan
   §1.3).
2. **For Sol, the 4k retrieval contexts don't help, and slightly hurt.**
   - V drops significantly from closed book to S2 (−0.042), and V_strict drops from closed book to S1 (−0.036).
   - Even the oracle context only matches closed book on V_strict (0.446 vs 0.445).
   - What retrieval still gives Sol: grounding (quotes, linked sources) and, with the oracle, fewer contradictions.

   The trend seen with Terra (H1) is stronger with Sol, as hypothesised. On V_strict it is not significant as a
   difference in differences; on V it is.
3. **The S2 > S1 result holds for Sol** (+0.013, p 0.09; Terra +0.018, p 0.08). Its size does not depend on the
   generator here (H5).
4. **Confounds to state in the paper:**
   - generation (6.2 vs 5.6) and tier (Sol vs Terra) are not separated: no `gpt-6.2-terra` exists, and the optional
     `gpt-6.1-terra` control was not run (D3);
   - Sol ran at reasoning effort `minimal`, Terra at `none`. Reasoning tokens appear in 43% of Sol's closed-book
     answers (31 tokens on average) and almost never with a context, so the closed-book advantage could owe a
     little to it;
   - batch vs flex serving should not matter (same model, same parameters, served by OpenAI).
